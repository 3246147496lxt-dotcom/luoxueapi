# 落雪额度查看器产品需求（P0）

状态：核心口径与视觉方案已确认；真实本周期用量已接入

适用范围：独立 macOS / Windows 查看器，不接入现有 `desktop/`

## 1. 产品定义

落雪额度查看器不是缩小版数据看板，而是覆盖整账户的额度状态助手。
客户打开应用后，应在 10 秒内回答：

1. 从余额或会员额度角度看，哪些 API Key 当前没有被额度阻塞；
2. 它们使用账户余额还是会员额度；
3. 当前权益还剩多少、何时恢复；
4. 受限后应该充值、等待重置、续费，还是调整 API Key 分组。

查看器统计当前账户下的全部启用 API Key，不按当前设备、单个 Key 或某个客户端统计。

## 2. 已确认的业务口径

### 2.1 计费由 API Key 分组决定

- 标准计费分组的 API Key 只扣账户雪花余额；
- 会员分组的 API Key 只扣对应会员的 7 天额度；
- 会员额度耗尽后不会自动改扣账户余额；
- 余额与会员额度互不合并，不得显示“账户总额度”；
- 整账户只能显示“全部额度正常 / 部分额度受限 / 全部额度受限 / 未知”，具体额度状态必须落实到计费分组；
- 额度正常不等于单次请求必然成功，模型、路由、RPM、并发和上游状态不属于本产品的判断范围。

面向客户的文案使用“余额计费 Key”和“会员 Key”；“分组”只在设置或详情中用于解释计费规则。

### 2.2 账户余额

- 名称固定为“账户余额”；
- 单位为雪花额度，展示格式如 `❄128.64`；
- 余额没有使用百分比，也没有重置时间；
- 冻结或预留额度只在大于 0 时显示，并明确说明其不可立即使用；
- 余额不足只能影响余额计费 Key，不能据此判断整个账户不可用。

### 2.3 会员额度

- 每份会员只有一个 7 天额度窗口；
- 不展示日额度、自然周额度或月额度；
- 周期锚点是会员开通时间，而不是首次调用时间或自然周起点；
- 当前周期为 `[starts_at + N × 7 天, starts_at + (N + 1) × 7 天)`；
- 7 天按连续 `7 × 24` 小时计算，服务端返回准确的 `period_start`、`period_end` 和 `resets_at`；
- 未中断续费沿用原周期锚点；
- 会员过期后重新开通，或切换为新套餐时，以新套餐生效时间建立新锚点；
- 服务端百分比固定表示“已用百分比”；首页环形图固定显示并明确标注“剩余百分比”，同时展示已用、限额和剩余，详情页再展示准确重置时间；
- 会员到期与额度重置是两个不同事件，必须分别展示。

### 2.4 不做 Codex 平台额度

P0 删除“Codex 平台额度”及任何由余额反推 Token 的伪额度。

原因：

- 不同模型、输入/输出、缓存、图片和分组倍率的单位成本不同；
- 价格配置会变化，余额无法稳定换算为可用 Token；
- 当前不存在用户级 Codex 模型额度的真实分母；
- 上游账号池额度属于内部资源，不能冒充客户权益。

未来如需提供 Token 成本估算，应作为独立估算工具，明确标注“估算”，不得进入额度状态。

允许展示服务端记录的当前会员本周期真实请求数与 Token 用量。它们只是辅助统计，不是“可用 Token 额度”，也不参与会员额度、剩余百分比或可用状态的计算。

## 3. 用户与核心场景

### 3.1 余额计费客户

需要快速确认账户余额是否足以支持余额计费 Key，并在余额不足时前往充值。

### 3.2 会员客户

需要确认会员 Key 的 7 天额度、剩余量、准确重置时间和会员到期时间。

### 3.3 同时使用两种计费方式的客户

需要分别看到余额计费 Key 和会员 Key 的状态。任一类受限时，应用必须说明另一类是否仍可用，不能暗示自动切换计费来源。

## 4. P0 信息架构

### 4.1 首页

共同信息：

- 脱敏账户标识；
- 数据范围“全部 API Key”；
- 整账户汇总状态；
- 最后成功更新时间；
- 手动刷新入口；
- 与当前阻塞原因一致的唯一主操作。

余额区域（存在余额计费 Key 时显示）：

- 可用余额；
- 冻结或预留额度（仅大于 0 时）；
- 使用余额计费的启用 Key 数量；
- 状态：可用、余额不足或未知；
- 余额不足时提供“前往充值”。

会员区域（存在有效会员或会员 Key 时显示）：

- 会员名称；
- 使用该会员的启用 Key 数量；
- 环形图“剩余 XX%”；
- 已用、限额和剩余雪花额度；
- 当前周期准确结束时间；
- 会员到期时间；
- 当前会员本周期从 `period_start` 到当前时间的已记录请求数与 Token 总量；
- 状态：可用、即将耗尽、已耗尽、已过期、已暂停或未知。

首页禁止展示：

- 预计可用 Token/请求数、模型分布和单请求明细；
- 与当前会员没有明确归属关系的账户级趋势和账单流水；
- 上游平台或账号池额度；
- 日/月会员额度；
- 单个请求明细；
- 钱包与会员相加后的“总额度”；
- 无上下文的“账户可用”布尔状态。

### 4.2 会员详情

- 会员名称和状态；
- 开通时间与到期时间；
- 当前 7 天周期开始、结束和重置时间；
- 已用、限额、剩余和已用百分比；
- 使用该会员额度的 API Key 名称与脱敏标识；
- 当前会员本周期的请求数、Token 总量及按日 Token 分类图表；
- 固定说明：“会员额度耗尽后，会员 Key 不会自动改扣账户余额”；
- 前往网站管理会员或 API Key 的入口。

### 4.3 余额详情

- 可用余额；
- 冻结或预留额度；
- 使用余额计费的 API Key 名称与脱敏标识；
- 前往网站充值、查看账单或管理 API Key 的入口。

P0 不在应用内复制完整账单流水。

### 4.4 设置

- 当前账户、退出连接和管理已授权设备；
- 开机启动；
- 自动刷新间隔：5、15、30 分钟；
- 余额不足通知阈值；
- 会员额度达到 70%、90%、100% 的通知；
- 会员即将到期通知；
- 是否隐藏具体金额；
- 语言、主题、检查更新和版本信息；
- 打开网站、管理 API Key、管理会员。

应用内不得要求用户粘贴具有消费能力的 API Key。

## 5. 状态和操作

| 状态 | 首屏结论 | 必须说明 | 唯一主操作 |
|---|---|---|---|
| 余额和会员均可用 | 全部额度正常 | 两类 Key 的计费来源、会员剩余与重置时间 | 查看详情 |
| 会员已用 90%–99.99% | 会员额度即将用完 | 剩余量、重置时间、耗尽后会员 Key 会暂停且不回退余额 | 查看会员详情 |
| 会员已耗尽但余额计费 Key 可用 | 部分额度受限 | 会员 Key 已暂停；余额计费 Key 仍可用；二者不会自动切换 | 管理 API Key |
| 余额不足但会员 Key 可用 | 部分额度受限 | 余额计费 Key 已暂停；会员 Key 仍可用 | 前往充值 |
| 两类权益均不可用 | 全部额度受限 | 每类阻塞原因和最早恢复时间 | 根据最先可恢复的原因显示充值、等待或续费 |
| 有权益但没有启用 Key | 暂无 API Key | 当前权益存在，但没有可调用的 Key | 前往创建 Key |
| 刷新失败且有缓存 | 数据已过期 | 所有数字均为上次数据、最后成功更新时间 | 重新获取 |
| 刷新失败且无缓存 | 无法获取 | 不得用 0 余额或 0% 代替未知数据 | 重新获取 |
| 设备授权失效 | 需要重新连接 | 本地缓存不再视为当前状态 | 连接账户 |

状态优先级：授权失效 > 无数据 > 数据过期 > 全部额度受限 > 部分额度受限 > 即将耗尽 > 全部额度正常。

## 6. 关键流程

### 6.1 首次连接

安装应用 → 浏览器确认只读授权 → 回到应用 → 拉取整账户摘要 → 展示各计费分组状态。

### 6.2 工作前快速确认

打开托盘面板 → 先展示带更新时间的安全缓存 → 后台刷新 → 10 秒内确认哪些 Key 可用、扣哪类权益以及何时恢复。

### 6.3 会员额度提醒

收到阈值通知 → 打开会员详情 → 查看剩余量和重置时间 → 必要时等待重置或前往管理 API Key。不得提示充值可以恢复会员 Key。

### 6.4 离线或服务故障

保留上次成功数据 → 标记“上次数据”及时间 → 禁止根据旧数据继续宣称当前可用 → 提供重试。

## 7. P0 非目标

- 多账户同时登录；
- 应用内充值、购买会员或修改 API Key；
- API Key 创建、编辑和分组切换；
- 模型消费分析、单请求分析和完整账单/日志；
- 预计可用 Token、请求数或使用时长；
- Codex、OpenAI、Anthropic 等上游账号池额度；
- 原生系统小组件；
- CSV 导入导出；
- 完整账单与请求日志。

## 8. 验收标准

- 首页聚合当前账户全部启用 API Key，不使用单个 Key 冒充整账户；
- 每个 API Key 只有一个明确的计费来源；
- 余额计费 Key 只受余额影响，会员 Key 只受对应会员额度影响；
- 会员耗尽时，即使余额大于 0，会员 Key 仍显示不可用；
- 充值不得被描述为恢复会员 Key 的方式；
- 会员只出现一个从开通时间锚定的 7 天窗口；
- 7 天周期由服务端返回，客户端不按自然周或本地时间推算；
- 余额、会员额度和任何上游额度不得相加；
- 多个分组状态不一致时，整账户显示“部分额度受限”；
- 应用不得把“额度正常”渲染成对模型、路由、RPM、并发或上游可用性的保证；
- 首页环形百分比必须写成“剩余 XX%”；其他位置如展示百分比，必须明确写成“已用”或“剩余”，不得只显示裸百分比；
- 无限、未知、禁用和不可适用状态不得显示为 0%；
- 首次请求失败不得显示余额 0 或使用率 0；
- 缓存数据必须显示最后成功更新时间和过期状态；
- API Key 只显示名称和脱敏标识，不暴露完整密钥；
- 本周期统计只包含归属于当前会员且发生于权威周期范围内的请求，不混入余额计费、其他会员或其他周期；
- 成功查询但无请求时显示真实 0；查询失败或数据不可确认时显示未知，不得用 0 代替；
- 请求数和 Token 统计不参与会员环、剩余额度或可用状态计算；
- 同一会员周期内，同一阈值只通知一次；
- 五名不了解实现细节的客户均能在 10 秒内回答：哪些 Key 可用、扣哪类权益、哪类已受限、何时恢复以及下一步操作。

## 9. 实现约束

- 新会员开通时立即将 7 天窗口锚定到准确的 `starts_at`；
- 过期后重新开通时使用准确的新 `starts_at`，不得截到当天零点；
- 未中断续费只延长到期时间，不改变原锚点；
- 服务端统一返回权威的周期开始、结束和重置时间。
- `period_usage` 必须按用户、会员和权威周期边界聚合；聚合失败只降级本周期用量，不影响余额与会员剩余额度。
